# 실행 로드맵과 진행 현황

- 최종 갱신일: 2026-11-15 (Asia/Seoul)
- 최종 목표: [PLAN.md](PLAN.md) / 상세 요구사항: [REQUIREMENTS.md](REQUIREMENTS.md)
- 현재 위치: **M0-01~09 완료. M0-09는 새 NSPL 12T의 shift_reg_8bit로 QFlow 합성·GrayWolf 배치·QRouter 배선 후 별도 DEF/전원 보정·KLayout GDS 조립까지 실제 최소 실험을 통과했다. 공유 etri050·원본을 보존하고 최초 실패·수정·독립 재현·GDS 결함 검출을 기록했다. 이는 제한된 호환성 실험이며 CTS·검증된 RC·STA·DRC/LVS를 포함한 전체 흐름 통과가 아니다. M0-10의 CTS/RC 실험, M0-11/12의 backend 선택, 공통 계약은 미착수. M0-08의 전체 라이브러리 재특성화·동시 R/S 해제 한계도 유지한다.**
- 기준 예제: `shift_reg_8bit` → 확장 예제 FIR.
- 이후 단계의 입력: [전체 PDK/PDF 조사](experiments/pdk-package-review/README.md)와 [PDK 참고 자료](PDK_REFERENCE.md)를 M0-10 이후에 적용한다. 완료된 M0-01~09의 작업·상태·근거는 보존한다.
- Codex 실행 안내: [모델·effort와 작업별 프롬프트](CODEX_GUIDE.md).

이 파일에서 **실행 순서, 작업별 상태, 다음 행동, 완료 근거, 최초 릴리스 점검**을 함께 관리한다. `PLAN.md`에는 최종 목표를, `REQUIREMENTS.md`에는 상세 요구사항을 두고, 이 파일에는 그 목표를 실제로 진행하는 작업과 상태를 둔다. 아직 실행하지 않은 구현·검증을 완료로 표시하지 않는다.

M0·M1은 Codex를 활용하여 조사·실험·코드 작성·검증·기록까지 진행할 수 있다. 프롬프트를 추가한 것만으로 해당 개발 작업의 상태를 바꾸지는 않는다. M3·M4는 후속 작업 후보이며 수행 여부는 추후 결정한다.

## 1. 진행 상황을 갱신하는 방법

| 상태 | 사용 기준 |
| --- | --- |
| 미착수 | 작업을 시작하지 않음 |
| 진행 중 | 실제 작업을 시작했고 다음 행동이 정해짐 |
| 대기 | 선행 작업·자료·결정이 필요함. 필요한 항목과 해제 조건을 기록함 |
| 완료 | 해당 작업의 완료 조건을 충족하고 문서·실험·검토 결과 등 근거를 연결함 |

위 상태는 **개발 작업의 상태**다. 설계 실행의 `passed`/`failed`/`blocked`/`estimated` 등은 [상세 요구사항의 공통 결과 판정](REQUIREMENTS.md#공통-결과-판정과-재실행)을 따른다. 검증할 수 없다는 결론을 얻은 실험은 그 조사 작업을 완료할 수 있지만, 대상 설계나 후속 검증이 통과한 것은 아니다.

작업 시 다음 순서로 갱신한다.

1. 착수할 행의 상태·다음 행동을 갱신한다. M2의 A/B/C는 [분담표](REQUIREMENTS.md#8-3명의-분담과-인계)를 따른다.
2. 작업 중 발견한 시행착오는 `development/experiments/`, 선택한 방안과 이유는 `development/decisions/`, 인계 검증은 `development/handoffs/`에 기록하고 해당 행에서 연결한다. 이 하위 폴더들은 필요한 기록을 만들 때 생성한다.
3. 완료 시 산출물과 검증 결과를 연결한다. 막히면 필요한 자료·선행 작업·해제 조건과 다음 행동을 적는다. 이 파일의 작업 ID는 유지하고, 새 작업에는 새 ID를 부여한다.
4. 영향을 받는 작업의 상태와 최종 갱신일을 수정한다. 현재 위치가 바뀌면 첫머리의 현재 위치도 갱신하고, 주요 변동은 마지막 변경 기록에 남긴다.
5. 완료된 단계의 작업·상태·근거·기존 기록을 소급 수정하지 않는다. 새 자료·요구사항이나 기존 근거를 재검토할 문제가 생기면 미완료 후속 단계 또는 새 작업에 사유·영향·검증 조건을 적는다. 필요한 후속 검증이 끝나기 전에는 전체 목표를 완료로 판정하지 않는다.

상태표와 릴리스 체크리스트는 이 파일에서만 갱신한다. 상세 기록에는 실험·결정의 내용을 적고 이 파일을 연결하여 진행 상태가 여러 곳에 중복되지 않게 한다.

#### 초기에 함께 결정할 기술 선택의 실행 방법

상세 요구사항의 [초기 기술 선택](REQUIREMENTS.md#초기에-함께-결정할-기술-선택)을 M0-09~12로 구체화한다. **QFlow 호환성 실험과 CTS·RC 경로 확인을 함께 진행하고, 두 결과를 보고 기본 경로를 정한 뒤 공통 개발 계약에 반영한다.**

1. **M0-09 — 기존 흐름에서 확인:** 작은 `shift_reg_8bit` 설계와 동일한 새 PDK view 세트로 셀 읽기 → 합성 → 배치 → 배선 → GDS 인계를 확인한다. 실패하면 최초 실패 위치와 최소 재현 입력, 필요한 어댑터 변경을 기록한다. 셀 기능 모델 불일치 등 미해결 항목은 우회로 숨기지 않는다.
2. **M0-10 — CTS와 RC 경로 확인:** 제공 Util의 CTS 셀·track/PG와 ITF/ICT/MIPT·RC 자료를 출발점으로, 도구·버퍼·RC 변환, skew 지표, 최종 배선 기생성분 생성·OpenSTA 검증 경로를 함께 정한다. 출처·단위·RC 코너, 채택한 SPEF 또는 검증된 SDF의 포함 범위와 annotation 누락 확인법을 기록한다. 셀별 PEX와 전체 배선 기생성분을 구분하고 SPEF 채택 시 SDF 병행 생성을 필수화하지 않는다.
3. **M0-11 — 기본 경로 선택:** 앞의 실험으로 QFlow 보완 또는 OpenROAD 기반 경로 중 필요한 기능을 충족하는 한 가지를 선택한다. 모든 대안을 완성하지 않고 미채택 이유·남은 위험을 기록한다. 혼합 경로를 채택할 때 DEF/netlist의 instance·net 이름, 클록·전원 연결, 층·단위의 실제 도구 경계를 최소 사례로 검증한다.
4. **M0-12 — 결정 근거 보존:** 비교한 방안, 실험 링크·도구/PDK 버전, 선택 이유, 지원 한계, 미해결 과제를 `development/decisions/`에 남긴다. 어떤 결과가 나오면 결정을 다시 검토할지도 적고, M0-13의 공통 계약과 이후 설치·튜토리얼에 반영한다.

RC가 없거나 근사치뿐이면 실행 결과를 `estimated`/`blocked`로, CTS가 없으면 ideal-clock 분석으로 명시한다. 이런 결과를 검증된 POST-STA 완료로 처리하지 않는다. 대안의 타당성은 도구 기능 목록만으로 판단하지 않고 최소 실험 결과로 확인한다.

**선택 의존 관계:** M0-09 + M0-10 → M0-11 → M0-12 → M0-13. M0-07/08의 라이브러리 검증과 M0-06의 지원 조건도 각 실험·공통 계약에 반영한다.

M0-14의 용도·참조 조사는 다른 M0 작업과 병행할 수 있다. 최종 보존 범위와 목표 경로는 선택한 backend·공통 계약을 반영해 확정하고, M0의 비교용 원본·최소 재현 입력·로그를 보존하여 M1의 이행 전후 검증에 사용한다.

## 3. 최초 릴리스 체크리스트

마일스톤별 작업이 끝나면 아래 기준을 최종 점검한다. 체크할 때 관련 작업 ID와 실제 검증 근거를 이 절의 근거 표에 기록한다. 첫 릴리스 범위는 M0-06에서 확정하고 [코어 설계와 칩 완성의 구분](REQUIREMENTS.md#코어-설계-완료와-실제-칩-완성의-구분)을 따른다.

- [ ] **R-01** 깨끗한 지원 환경에서 README만으로 도구 setup/build와 PDK 점검을 수행할 수 있다.
- [ ] **R-02** `scripts/new-project.sh fir`가 독립된 프로젝트와 작성할 초기 설정을 만든다.
- [ ] **R-03** YAML을 모르는 사용자도 구조를 바꾸지 않고 칸별 안내·완성 예를 참고하여 필수 빈칸을 채울 수 있다.
- [ ] **R-04** 다섯 단계의 튜토리얼·설정·명령·프롬프트·관련 lessons가 서로 연결되어 있다.
- [ ] **R-05** AI가 도움이 되는 시나리오마다 복사·붙여넣기 프롬프트와 공식 자료에 근거한 권장 모델·effort·확인일이 함께 제공된다.
- [ ] **R-06** `shift_reg_8bit`와 FIR가 같은 공통 실행 경로를 사용한다.
- [ ] **R-07** 새 PDK view가 일관되게 사용되고, 기능 모델·전원·층·격자·제공 규칙/RC 출처·변환·검증 범위가 설명되어 있다. 적용 가능한 미검증 timing/물리 항목의 사유가 공개되어 있다.
- [ ] **R-08** 상용 EDA 없이 필수 검증을 수행하며, 검증하지 못한 항목을 합격으로 표시하지 않는다.
- [ ] **R-09** 결과와 로그가 실행별로 보존되고, 입력 변경 후 오래된 결과가 통과로 재사용되지 않는다.
- [ ] **R-10** 설치·예제·문서 링크에 기존 실습 폴더의 숨은 의존성이 없다.
- [ ] **R-11** 개발 판단·시행착오는 `development/`에, 재사용 가능한 조언은 `docs/lessons/`에 정리되어 있다.
