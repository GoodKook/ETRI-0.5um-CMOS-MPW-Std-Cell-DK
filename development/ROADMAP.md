# 실행 로드맵과 진행 현황

- 최종 갱신일: 2026-11-15 (Asia/Seoul)
- 최종 목표: [PLAN.md](PLAN.md) / 상세 요구사항: [REQUIREMENTS.md](REQUIREMENTS.md)
- 현재 위치: **A/B/C가 빠르게 독립 개발을 시작할 공통 환경·폴더·최소 계약 준비를 우선한다. M0-01~09의 완료 기록은 유지하고, M0-10~12의 미완료 CTS/RC·최종 backend 선택은 M2-02/03/05로 이관한다. 다음 실행은 M0-13/14 → M1-01~08 → 아래 M2 착수 기준 확인이다. 공통 준비와 M2는 아직 완료되지 않았다.**
- 기준 예제: `shift_reg_8bit` → 확장 예제 FIR.
- 이후 단계의 입력: [전체 PDK/PDF 조사](experiments/pdk-package-review/README.md)와 [PDK 참고 자료](PDK_REFERENCE.md)를 M0-10 이후에 적용한다. 완료된 M0-01~09의 작업·상태·근거는 보존한다.
- Codex 실행 안내: [모델·effort와 작업별 프롬프트](CODEX_GUIDE.md).
- 담당자 진입점: [M2 인계 준비와 담당별 시작 자료](handoffs/M2-PREPARATION.md). M0-10 실험은 이관 참고 자료로 보존하며 공통 준비에서 추가 실험을 계속하지 않는다.

이 파일에서 **실행 순서, 작업별 상태, 다음 행동, 완료 근거, 최초 릴리스 점검**을 함께 관리한다. `PLAN.md`에는 최종 목표를, `REQUIREMENTS.md`에는 상세 요구사항을 두고, 이 파일에는 그 목표를 실제로 진행하는 작업과 상태를 둔다. 아직 실행하지 않은 구현·검증을 완료로 표시하지 않는다.

M0·M1은 Codex를 활용하여 조사·실험·코드 작성·검증·기록까지 진행할 수 있다. 프롬프트를 추가한 것만으로 해당 개발 작업의 상태를 바꾸지는 않는다. M3·M4는 후속 작업 후보이며 수행 여부는 추후 결정한다.

## 1. 진행 상황을 갱신하는 방법

| 상태 | 사용 기준 |
| --- | --- |
| 미착수 | 작업을 시작하지 않음 |
| 진행 중 | 실제 작업을 시작했고 다음 행동이 정해짐 |
| 대기 | 선행 작업·자료·결정이 필요함. 필요한 항목과 해제 조건을 기록함 |
| 이관 | 원래 작업은 미완료이며 명시한 후속 작업·담당자가 이어서 수행함. 공통 준비를 막지 않으며 원래 검증의 통과를 뜻하지 않음 |
| 완료 | 해당 작업의 완료 조건을 충족하고 문서·실험·검토 결과 등 근거를 연결함 |

위 상태는 **개발 작업의 상태**다. 설계 실행의 `passed`/`failed`/`blocked`/`estimated` 등은 [상세 요구사항의 공통 결과 판정](REQUIREMENTS.md#공통-결과-판정과-재실행)을 따른다. 검증할 수 없다는 결론을 얻은 실험은 그 조사 작업을 완료할 수 있지만, 대상 설계나 후속 검증이 통과한 것은 아니다.

현재 우선 목표는 **세 사람이 공통 구조에서 각자 조사·튜토리얼·실행 코드를 개발할 수 있도록 인계하는 것**이다. 실제 CTS·RC·POST-STA·물리 검증 기준은 유지하고 M2의 담당 업무에서 충족한다. `이관` 행은 공통 준비의 완료 판정에서 제외하며 남은 실제 검증은 연결된 M2 행에서 추적한다. 이관만으로 M0-10~12를 완료했다고 쓰지 않는다.

작업 시 다음 순서로 갱신한다.

1. 착수할 행의 상태·다음 행동을 갱신한다. M2의 A/B/C는 [분담표](REQUIREMENTS.md#8-3명의-분담과-인계)를 따른다.
2. 작업 중 발견한 시행착오는 `development/experiments/`, 선택한 방안과 이유는 `development/decisions/`, 인계 검증은 `development/handoffs/`에 기록하고 해당 행에서 연결한다. 이 하위 폴더들은 필요한 기록을 만들 때 생성한다.
3. 완료 시 산출물과 검증 결과를 연결한다. 막히면 필요한 자료·선행 작업·해제 조건과 다음 행동을 적는다. 이 파일의 작업 ID는 유지하고, 새 작업에는 새 ID를 부여한다.
4. 영향을 받는 작업의 상태와 최종 갱신일을 수정한다. 현재 위치가 바뀌면 첫머리의 현재 위치도 갱신하고, 주요 변동은 마지막 변경 기록에 남긴다.
5. 완료된 단계의 작업·상태·근거·기존 기록을 소급 수정하지 않는다. 새 자료·요구사항이나 기존 근거를 재검토할 문제가 생기면 미완료 후속 단계 또는 새 작업에 사유·영향·검증 조건을 적는다. 필요한 후속 검증이 끝나기 전에는 전체 목표를 완료로 판정하지 않는다.

상태표와 릴리스 체크리스트는 이 파일에서만 갱신한다. 상세 기록에는 실험·결정의 내용을 적고 이 파일을 연결하여 진행 상태가 여러 곳에 중복되지 않게 한다.

**지금의 실행 경로:** M0-01~09의 기존 결과 + M0-10의 조사·실패 인계 → M0-13/14 → M1-01~08 → M2 병행 착수.

**담당자 작업 경로:** B의 M2-02에서 최종 backend·CTS·route·RC 생성 → C의 M2-03과 공동 검증, M2-05에서 실제 인계 확인. 이 작업들의 완료를 공통 schema·프로젝트 생성기의 선행조건으로 두지 않는다. C는 실제 배선 완료 전에도 명확히 표시한 fixture로 보고서·누락 검출·문서 개발을 시작할 수 있다.

팀이 사용하지 않는 legacy 전체 이동·삭제와 모든 후보 도구의 설치·빌드는 착수 조건에 넣지 않는다. 실제 사용하는 코드·모델·설정·필수 외부 참조는 이행 시 함께 수정·검증한다.

#### 초기에 함께 결정할 기술 선택의 실행 방법

이 절은 2026-11-15의 **빠른 병행 개발 인계** 방침을 적용한다. 완료된 M0-01~09의 행·근거는 당시 기록대로 유지한다.

1. 기존 조사의 지원 OS·PDK export·제한 셀 프로파일과 실제 성공/실패 범위를 공유한다. 같은 실험을 반복해 준비 기간을 늘리지 않는다.
2. 지금 확정할 것은 팀 사용 경로, 공통 YAML/CLI·결과·인계 계약, SPEF 우선 인터페이스와 fixture 표시 방식이다. 후보 backend의 내부 구현까지 고정할 필요는 없다.
3. M0-10~12의 실제 CTS/RC·최종 backend 선택은 M2-02/03/05로 이관한다. B는 생산 경로를, C는 annotation·POST-STA와 검증 범위를 담당하고 RC 정확도·인계는 공동 검증한다.
4. 이관으로 검증 기준을 낮추지 않는다. 기존 실제 RC/POST-STA 결과는 계속 blocked이고, 근사 RC·ideal clock·fixture를 실제 설계의 passed로 승격하지 않는다.

**현재 선행 관계:** M0-06~09 + 기존 위험 인계 → M0-13/14 → M1. **담당자 구현 관계:** M2-02(B) ↔ M2-03(C), 실제 인계는 M2-05. M0-11/12의 최종 선택을 M0-13/14의 선행조건으로 두던 관계는 해제한다.
