# 실행 로드맵과 진행 현황

- 최종 갱신일: 2026-11-15 (Asia/Seoul)
- 목표·요구사항: [PLAN.md](PLAN.md)
- 현재 위치: **M0-01~09 완료. M0-09는 새 NSPL 12T의 shift_reg_8bit로 QFlow 합성·GrayWolf 배치·QRouter 배선 후 별도 DEF/전원 보정·KLayout GDS 조립까지 실제 최소 실험을 통과했다. 공유 etri050·원본을 보존하고 최초 실패·수정·독립 재현·GDS 결함 검출을 기록했다. 이는 제한된 호환성 실험이며 CTS·검증된 RC·STA·DRC/LVS를 포함한 전체 흐름 통과가 아니다. M0-10의 CTS/RC 실험, M0-11/12의 backend 선택, 공통 계약은 미착수. M0-08의 전체 라이브러리 재특성화·동시 R/S 해제 한계도 유지한다.**
- 기준 예제: `shift_reg_8bit` → 확장 예제 FIR.
- Codex로 시작하기: [모델·effort 설정](#51-모델effort-선택과-공식-근거)을 확인한 뒤 [M0·M1 일괄 진행 프롬프트](#p-all-m0m1-일괄-진행)를 복사한다. 작은 단위로 진행하려면 아래 작업표의 프롬프트를 사용한다.

이 파일에서 **실행 순서, 작업별 상태, 다음 행동, 완료 근거, 최초 릴리스 점검**을 함께 관리한다. `PLAN.md`에는 목표·설계 원칙·요구사항을 두고, 이 파일에는 그 목표를 실제로 진행하는 작업과 상태를 둔다. 아직 실행하지 않은 구현·검증을 완료로 표시하지 않는다.

M0·M1은 Codex를 활용하여 조사·실험·코드 작성·검증·기록까지 진행할 수 있다. 프롬프트를 추가한 것만으로 해당 개발 작업의 상태를 바꾸지는 않는다. M3·M4는 후속 작업 후보이며 수행 여부는 추후 결정한다.

## 1. 진행 상황을 갱신하는 방법

| 상태 | 사용 기준 |
| --- | --- |
| 미착수 | 작업을 시작하지 않음 |
| 진행 중 | 실제 작업을 시작했고 다음 행동이 정해짐 |
| 대기 | 선행 작업·자료·결정이 필요함. 필요한 항목과 해제 조건을 기록함 |
| 완료 | 해당 작업의 완료 조건을 충족하고 문서·실험·검토 결과 등 근거를 연결함 |

위 상태는 **개발 작업의 상태**다. 설계 실행의 `passed`/`failed`/`blocked`/`estimated` 등은 [PLAN.md의 공통 결과 판정](PLAN.md#공통-결과-판정과-재실행)을 따른다. 검증할 수 없다는 결론을 얻은 실험은 그 조사 작업을 완료할 수 있지만, 대상 설계나 후속 검증이 통과한 것은 아니다.

작업 시 다음 순서로 갱신한다.

1. 착수할 행의 상태·다음 행동을 갱신한다. M2의 A/B/C는 [분담표](PLAN.md#10-3명의-분담과-인계)를 따른다.
2. 작업 중 발견한 시행착오는 `development/experiments/`, 선택한 방안과 이유는 `development/decisions/`, 인계 검증은 `development/handoffs/`에 기록하고 해당 행에서 연결한다. 이 하위 폴더들은 필요한 기록을 만들 때 생성한다.
3. 완료 시 산출물과 검증 결과를 연결한다. 막히면 필요한 자료·선행 작업·해제 조건과 다음 행동을 적는다. 이 파일의 작업 ID는 유지하고, 새 작업에는 새 ID를 부여한다.
4. 영향을 받는 작업의 상태와 최종 갱신일을 수정한다. 현재 위치가 바뀌면 첫머리의 현재 위치도 갱신하고, 주요 변동은 마지막 변경 기록에 남긴다.
5. 완료 근거가 무효화되면 해당 작업을 다시 열고 이유를 남긴다. 날짜를 추정하여 채우거나, 체크리스트를 작성했다는 이유만으로 설계 검증을 완료 처리하지 않는다.

상태표와 릴리스 체크리스트는 이 파일에서만 갱신한다. 상세 기록에는 실험·결정의 내용을 적고 이 파일을 연결하여 진행 상태가 여러 곳에 중복되지 않게 한다.

#### 초기에 함께 결정할 기술 선택의 실행 방법

기존 `PLAN.md` 3절의 기술 선택을 M0-09~12로 구체화한다. **QFlow 호환성 실험과 CTS·RC 경로 확인을 함께 진행하고, 두 결과를 보고 기본 경로를 정한 뒤 공통 개발 계약에 반영한다.**

1. **M0-09 — 기존 흐름에서 확인:** 작은 `shift_reg_8bit` 설계와 동일한 새 PDK view 세트로 셀 읽기 → 합성 → 배치 → 배선 → GDS 인계를 확인한다. 실패하면 최초 실패 위치와 최소 재현 입력, 필요한 어댑터 변경을 기록한다. 셀 기능 모델 불일치 등 미해결 항목은 우회로 숨기지 않는다.
2. **M0-10 — CTS와 RC 경로 확인:** CTS를 수행할 도구·버퍼·RC 설정, skew 등 확인 지표, 최종 배선에서 기생성분을 생성하고 OpenSTA로 검증할 경로를 함께 정한다. 제공 RC 자료의 출처·단위·코너, SPEF 또는 검증된 SDF의 포함 범위와 annotation 누락 확인법을 기록한다. 셀별 PEX와 전체 배선 기생성분을 구분한다.
3. **M0-11 — 기본 경로 선택:** 앞의 실험으로 QFlow를 보완할지 P&R을 OpenROAD 기반으로 전환할지 선택한다. 혼합 경로라면 DEF/netlist의 instance·net 이름, 클록·전원 연결, 층·단위가 도구 간 왕복에서도 보존되는지 최소 사례로 검증한다. 사용자용 기본 경로는 한 가지로 정한다.
4. **M0-12 — 결정 근거 보존:** 비교한 방안, 실험 링크·도구/PDK 버전, 선택 이유, 지원 한계, 미해결 과제를 `development/decisions/`에 남긴다. 어떤 결과가 나오면 결정을 다시 검토할지도 적고, M0-13의 공통 계약과 이후 설치·튜토리얼에 반영한다.

RC가 없거나 근사치뿐이면 실행 결과를 `estimated`/`blocked`로, CTS가 없으면 ideal-clock 분석으로 명시한다. 이런 결과를 검증된 POST-STA 완료로 처리하지 않는다. 대안의 타당성은 도구 기능 목록만으로 판단하지 않고 최소 실험 결과로 확인한다.

**선택 의존 관계:** M0-09 + M0-10 → M0-11 → M0-12 → M0-13. M0-07/08의 라이브러리 검증과 M0-06의 지원 조건도 각 실험·공통 계약에 반영한다.

M0-14의 용도·참조 조사는 다른 M0 작업과 병행할 수 있다. 최종 보존 범위와 목표 경로는 선택한 backend·공통 계약을 반영해 확정하고, M0의 비교용 원본·최소 재현 입력·로그를 보존하여 M1의 이행 전후 검증에 사용한다.

## 5. M0·M1을 Codex로 진행하는 방법

이 절은 **이 리포지토리를 개발하는 M0·M1 작업용**이다. 향후 칩 설계 튜토리얼에 넣을 사용자 시나리오별 프롬프트는 [PLAN 9절](PLAN.md#9-튜토리얼-시나리오별-ai-사용-안내-요구사항)에 따라 별도로 작성한다.

한 번에 진행하려면 P-ALL, 작업과 모델을 바꾸며 진행하려면 작업표에 연결한 개별 프롬프트를 사용한다. 각 코드 블록은 그대로 복사할 수 있고, 저장소를 연 Codex가 실제 경로와 현재 상태를 읽도록 작성했다. 이미 완료된 M0-01~05는 필요한 근거만 확인하고 반복하지 않는다.

### 5.1 모델·effort 선택과 공식 근거

**공식 자료 확인일: 2026-11-14. 대상 실행 환경: 저장소 파일과 터미널에 접근할 수 있는 Codex/ChatGPT Work.** 모델은 프롬프트를 붙여넣기 전에 UI 또는 CLI에서 선택한다. 본문에 모델명을 적는 것만으로 실행 설정이 바뀌지는 않는다.

| 공식 자료 | 이 문서에서 사용하는 근거 |
| --- | --- |
| [OpenAI 모델 안내: 모델 선택](https://learn.chatgpt.com/docs/models#recommended-models) | 6.1 Sol은 복잡하고 장기간 이어지는 코드·문서 작업, 6.1 Terra는 글쓰기·시각 정보 등의 용도로 안내한다. 이를 근거로 구현·EDA 진단에는 Sol, 근거가 정리된 초보자 문서 작성에는 Terra를 제안한다. |

위 자료는 일반적인 모델·effort 선택 근거다. **작업별 추천은 이를 ETRI 개발 과제에 적용한 작성자의 제안이며, OpenAI가 이 PDK 작업에 특정 설정을 지정하거나 성능을 보증한 것은 아니다.** 실제 결과에 따라 조정한다.

| UI에서 선택할 이름 | CLI의 설정값 | 이 로드맵에서의 사용 기준 |
| --- | --- | --- |
| light | `low` | 이미 검증된 짧은 문구·표 정리 등 범위가 작은 작업에 사용 가능. |
| medium | `medium` | P-06의 환경 정리, P-106의 검증 근거 기반 안내 작성에 제안. |
| high | `high` | 구현·실험·검증을 함께 수행하는 P-ALL과 대부분의 개별 개발 작업에 제안. |
| extra high | `xhigh` | P-08의 순차 셀 의미 대조, P-10의 CTS·RC 연계처럼 오류 원인이 여러 파일·도구에 걸친 작업에 제안. |
| max | `max` | 범위를 좁힌 난제가 기존 시도로 해결되지 않고 더 깊은 분석이 필요할 때 P-DIAG에 선택적으로 사용. |
| ultra | `ultra` | 독립 과제를 하위 agent로 나눌 수 있을 때 P-ULTRA에 선택적으로 사용. 공통 파일 편집과 결과 통합은 상위 agent가 맡는다. |

`6.1 Sol`의 모델 ID는 `gpt-6.1-sol`, `6.1 Terra`는 `gpt-6.1-terra`다. Light는 CLI의 Low(`low`), Extra High는 `xhigh`로 표기한다. 실제 선택 가능 범위는 계정·클라이언트·모델에 따라 확인한다. Codex의 `/model`에서 모델과 effort를 선택할 수 있으며, 지원되는 Max/Ultra는 `More reasoning…`에서 확인한다. [공식 모델 설정 안내](https://learn.chatgpt.com/docs/models#choose-a-model)

CLI를 쓰는 경우 저장소 루트에서 다음과 같이 시작한 뒤 프롬프트를 붙여넣는다. 아래 명령은 전역 설정 파일을 수정하지 않는다.

```bash
# P-ALL 또는 일반 구현 작업
codex -m gpt-6.1-sol -c 'model_reasoning_effort="high"'

# P-08 / P-10
codex -m gpt-6.1-sol -c 'model_reasoning_effort="xhigh"'

# P-106: 구현 결과에 근거한 초보자 안내 작성
codex -m gpt-6.1-terra -c 'model_reasoning_effort="medium"'
```

### 5.2 모든 실행 프롬프트에 적용할 공통 규칙

아래 프롬프트는 이 절을 읽도록 지시하므로 공통 규칙을 매번 따로 붙여넣을 필요는 없다.

1. 저장소 루트와 적용되는 `AGENTS.md`, PLAN, ROADMAP, 현재 Git 변경을 먼저 확인한다. 기존 사용자 변경을 보존하고 관련 작업의 실제 상태·근거에서 이어서 진행한다.
2. 조사 결과만 제시하고 끝내지 말고, 요청한 범위의 코드·설정·문서·의미 있는 검증·진행 기록까지 수행한다. 완료 조건을 충족한 작업만 `완료`로 바꾼다.
3. 원본 PDK와 라이브러리 내용·수동 설계물·재현 근거를 보존하고, M0 실험에서 기존 공유 라이브러리나 시스템 기술 링크를 덮어쓰지 않는다. M1의 폴더 이행은 확정한 경로 대응표에 따라 참조를 함께 수정하고, 저장소 외부 링크에 미치는 영향도 확인한다. 외부 설정의 변경은 환경의 권한 절차를 따른다. 실험은 독립 디렉터리에서 수행하고 파생 어댑터·모델·변환의 출처와 해시를 남긴다.
4. 실제 사용한 RTL·설정·PDK·도구 버전, 명령과 작업 디렉터리, 로그·산출물, 기대/실제 결과를 `development/experiments/` 등에 기록한다. 대형 재생성 산출물은 보관 위치·해시·재실행 방법으로 연결한다.
5. 기술 선택은 실행 근거를 보고 Codex가 제안·채택·기록할 수 있다. 기능·타이밍 의도나 지원 정책을 자료에서 결정할 수 없을 때만 필요한 질문을 하고, 그 답을 기다리지 않아도 되는 작업은 계속한다.
6. 권한·네트워크·자료 때문에 실행할 수 없는 작업은 필요한 항목과 다음 명령을 기록하고 해당 행을 `대기`로 둔다. 실행하지 않은 빌드·시뮬레이션·물리 검증은 완료로 쓰지 않는다. 시스템 설치가 필요하면 환경의 권한 절차를 따르며 무조건적인 upgrade/autoremove나 전역 설정 덮어쓰기를 피한다.
7. RC 미확보·ideal clock·TT 한정·미이식 DRC 항목 등을 명시한다. 목표를 낮추거나 타이밍 예외·검증 생략으로 통과시키지 않는다. 모델 간 기능 불일치는 테스트벤치의 입력 시점만 조정하여 숨기지 않는다.
8. M0에서는 폴더 용도·의존성과 정리 계획을 조사하고, M1에서는 목표 구조로의 이행·정리·참조 수정과 설치·프로젝트 생성·설정 검사·기준 예제의 최소 동작 검증을 마친다. M2의 단계 실행이 아직 없으면 인터페이스와 미구현 상태를 명확히 표시하고, 성공을 반환하는 더미 실행기로 대체하지 않는다. 전체 흐름 통과는 별도 검증 대상이다.
9. 작업 종료·실제 장애 발생 시 ROADMAP의 해당 작업 행에 상태·근거·다음 행동을 갱신하고 현재 위치·변경 기록도 맞춘다. 최종 응답에는 완료 작업 ID, 변경 파일, 실제 검증, 미해결 항목, 다음 작업을 적는다.

### P-ULTRA. 독립 조사·검증을 나누어 진행

**선택 사항 / 추천: 6.1 Sol / ultra.** 하위 agent를 쓸 수 있는 환경에서 독립 과제를 분담하려는 경우에 사용한다. 기본 P-ALL의 필수 조건은 아니다.

```text
development/PLAN.md와 development/ROADMAP.md를 읽고 5.2의 공통 규칙에
따라 M0의 독립 조사·검증을 하위 agent에게 분담하여 진행해줘.
지원되는 하위 agent 수에 맞춰 PDK view inventory, 순차 셀 모델 검증,
QFlow·CTS·RC 도구/자료 적합성 조사를 나누고, 선행 자료가 필요한 실제
통합 실험은 그 자료가 준비된 다음 수행해줘.

각 하위 agent는 자기 실험 디렉터리와 개별 기록만 작성하게 하고,
ROADMAP·PLAN·공통 schema·공유 라이브러리는 동시에 수정하지 않게 해줘.
상위 agent가 결과를 대조·통합하여 충돌과 누락을 확인하고, 실제 완료한
작업만 ROADMAP에 반영해줘. 하위 agent를 쓸 수 없으면 그 사실을 밝히고
같은 분담 순서로 직접 수행해줘. 개발 작업의 완료 근거와 남은 장애를 보고해줘.
```
