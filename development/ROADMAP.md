- 조사 자료: [전체 PDK/PDF 조사](experiments/pdk-package-review/README.md), [PDK 참고 자료](PDK_REFERENCE.md).

이 파일에서 **실행 순서, 작업별 상태, 다음 행동, 완료 근거, 최초 릴리스 점검**을 함께 관리한다. `PLAN.md`에는 최종 목표를, `REQUIREMENTS.md`에는 상세 요구사항을 둔다. 상세 요구사항의 완성 형태는 M3의 구현·검증 기준이며, M2 착수에 필요한 항목은 아래 착수 기준으로 판단한다.

## 1. 진행 상황을 갱신하는 방법

| 상태 | 사용 기준 |
| --- | --- |
| 미착수 | 작업을 시작하지 않음 |
| 진행 중 | 실제 작업을 시작했고 다음 행동이 정해짐 |
| 대기 | 선행 작업·자료·결정이 필요함. 필요한 항목과 해제 조건을 기록함 |
| 완료 | 해당 작업의 완료 조건을 충족하고 문서·실험·검토 결과 등 근거를 연결함 |

위 상태는 **개발 작업의 상태**다. 설계 실행의 `passed`/`failed`/`blocked`/`estimated` 등은 [상세 요구사항의 공통 결과 판정](REQUIREMENTS.md#공통-결과-판정과-재실행)을 따른다. 조사·문서의 완료와 실제 설계의 기능·타이밍·물리 검증 통과를 구분한다.

1. 착수할 행의 상태·다음 행동을 갱신한다. A/B/C의 담당 범위는 [분담표](REQUIREMENTS.md#8-3명의-분담과-인계)를 따른다.
2. 시행착오는 `development/experiments/`, 기술 선택은 `development/decisions/`, 시작 자료와 인계 검증은 `development/handoffs/`에 기록하고 해당 행에서 연결한다. 같은 내용을 여러 문서로 나누어 중복 작성하지 않는다.
3. 완료 시 산출물과 확인 결과를 연결한다. 막히면 필요한 자료·선행 작업·해제 조건과 다음 행동을 적는다. 작업 ID는 유지하고 새 작업에는 새 ID를 부여한다.
4. 영향을 받는 작업의 상태·최종 갱신일·현재 위치를 맞추고, 실제 개발 결과는 변경 기록에 남긴다. 상태표와 릴리스 체크리스트는 이 파일에서만 갱신한다.
5. 완료된 단계의 작업·상태·근거·기존 기록을 소급 수정하지 않는다. 기존 실험의 입력·결과·실패도 보존한다. 추가 확인은 후속 작업에서 수행하며 실행하지 않은 검증을 완료로 표시하지 않는다.

**실행 경로:** 기존 조사·실험 → M0의 시작 자료·경로 정리 → M1의 작업 폴더·자료 접근 확인 → M2의 A/B/C 병렬 조사·집필 → M3의 담당별 구현·통합.

M0·M1은 [M2-PREPARATION.md](handoffs/M2-PREPARATION.md)에 자료 색인·규칙·경로·담당을 함께 정리하면 된다. 전체 YAML, 실행 가능한 스키마·CLI, 프로젝트 생성기, 설치 자동화, 신규 인계 fixture는 M3에서 개발한다. M2에서는 상대 담당자의 구현이나 실제 배선 산출물을 기다리지 않고 문서 초안을 작성한다.

#### 초기에 함께 결정할 기술 선택의 실행 방법

지원 OS·PDK export·제한 셀 프로파일은 기존 완료 근거를 사용한다. 공통 준비에서는 담당·경로·stage ID·입출력 종류만 정하고, 설계별 입력 칸과 도구별 설정은 M2 조사에 이어 M3에서 확정한다. 실제 backend 선택은 B가 주도하고 RC 정확도·annotation·최종 물리 검증은 C와 함께 확인한다.

기존 실험의 근사 RC·ideal clock·fixture와 실제 배선 결과를 구분한다. 실제 RC/POST-STA의 미검증 상태와 최종 검증 기준은 유지한다.
